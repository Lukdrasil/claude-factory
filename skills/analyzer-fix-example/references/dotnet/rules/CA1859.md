# CA1859: Use concrete types when possible for improved performance

**Analyzer**: Microsoft.CodeAnalysis.NetAnalyzers · **Kit config**: not configured; enabled by default as a suggestion (Info) in the .NET 10 SDK; an IDE-only hint, does not fail a warnings-as-errors build unless raised in `.editorconfig` · **Docs**: https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/quality-rules/ca1859

## Wrong

```csharp
namespace Kit.Modules.Orders.Application.Features.PriceOrder;

internal interface IPriceCalculator
{
    decimal Calculate(int quantity);
}

internal sealed class StandardPriceCalculator : IPriceCalculator
{
    public decimal Calculate(int quantity) => quantity * 9.99m;
}

internal sealed class OrderTotalService
{
    private readonly IPriceCalculator _calculator = new StandardPriceCalculator(); // interface field, only ever this one type

    public decimal Total(int quantity) => _calculator.Calculate(quantity);
}
```

## Right

```csharp
namespace Kit.Modules.Orders.Application.Features.PriceOrder;

internal interface IPriceCalculator
{
    decimal Calculate(int quantity);
}

internal sealed class StandardPriceCalculator : IPriceCalculator
{
    public decimal Calculate(int quantity) => quantity * 9.99m;
}

internal sealed class OrderTotalService
{
    private readonly StandardPriceCalculator _calculator = new();

    public decimal Total(int quantity) => _calculator.Calculate(quantity);
}
```

**Principle**: When a field or local is constructed with, and only ever holds, one concrete implementation, typing it concretely lets the JIT devirtualize and inline the call instead of paying interface-dispatch overhead for a polymorphism that never happens.

**Layer note**: Apply this only to locally-constructed fields/locals with a single implementation. A constructor-injected dependency crossing a Ports boundary (Application → Infrastructure) must stay interface-typed even if only one implementation is currently registered; that interface is what makes the dependency substitutable per DIP.
